# Reviewed HTML delivery and Cloudflare integration

The static Worker sets `Cache-Control: no-transform` on HTML documents, including admin, filtered game/Kids pages, 404s and corresponding 304 responses. Asset caching and non-HTML security responses keep their existing policy. CSP remains hash-based; no script origin, wildcard or `unsafe-inline` permission was added.

The audited live CDN appended a Cloudflare Web Analytics beacon and an inline JavaScript Detections bootstrap. Both were blocked by the declared script policy. The site already has explicit device consent for optional Google Analytics; an automatically injected second analytics client is outside that consent implementation. Preserving the reviewed HTML removes the blocked optional injection instead of weakening CSP.

Cloudflare documents that `no-transform` prevents [automatic Web Analytics injection](https://developers.cloudflare.com/web-analytics/get-started/) and [JavaScript Detections injection](https://developers.cloudflare.com/cloudflare-challenges/challenge-types/javascript-detections/). For JSD, `cf.bot_management.js_detection.passed` is then `missing`. This header does not turn off WAF rules, but rules depending on that field must be reviewed in the Cloudflare account. Account rules were not available during this source change; do not claim JSD-dependent protection is operational. The audited hash-based policy already prevented the injected bootstrap from executing.

If JSD is intentionally required, introduce Cloudflare's supported response-header nonce integration in a separately reviewed change, including cache correctness, frame policy, privacy behavior and actual WAF-rule verification. Do not suppress CSP errors by allowing broad inline scripts. After deployment, verify HTML is no longer modified, CSP violations from these injections disappear, and intended security challenges still work.

## Compression

`no-transform` also stops Cloudflare from compressing HTML ([Cache-Control interactions](https://developers.cloudflare.com/cache/concepts/cache-control/#gzip-and-other-compression)). Non-HTML assets do not carry `no-transform` and are still compressed by Cloudflare.

HTML is therefore compressed at build time. `scripts/build-static-site.mjs` writes a brotli (quality 11) and a gzip (level 9) copy of every deployable HTML page of at least 1 KiB to `/__precompressed/<sha256 of the page>.br` and `.gz`, after the publication and SEO scans have run on the final HTML. The build proves each copy decodes to exactly the published bytes, so the inline-script CSP hashes still match. The copies are ordinary release files: they are in `site-manifest.json`, the build ID and the 20,000-file Workers Free limit check, and `htmlPrecompression.variants` maps each page to its copies.

The Worker never compresses. For a `GET` of an HTML page (200 or the 404 page) it reads the visitor's own `Accept-Encoding` from `request.cf.clientAcceptEncoding` (Cloudflare rewrites the header itself; see [Cloudflare HTTP headers](https://developers.cloudflare.com/fundamentals/reference/http-headers/#accept-encoding)), prefers `br`, then `gzip`, fetches the stored copy, and returns it with `Content-Encoding`, `Vary: Accept-Encoding`, `Content-Type: text/html; charset=utf-8`, no `Content-Length`, the page's own weak ETag and `encodeBody: "manual"` so the runtime passes the bytes through. `HEAD`, `Range` requests, visitors that name neither coding, a missing or unexpected copy, and any other doubt fall back to the uncompressed page exactly as before. Identity responses and 304s for these pages also send `Vary: Accept-Encoding`. `/__precompressed/` paths are never served as pages: the Worker answers them with the 404 page and refuses a manifest that routes to one or lists a copy that does not match its page.

`src/index.js` adds the Worker version header to the same `Response` object. Cloudflare's [Response documentation](https://developers.cloudflare.com/workers/runtime-apis/response/) says Workers "compress data according to the `content-encoding` header when transmitting"; for data that is already compressed `encodeBody` "has to be set to `"manual"`, otherwise the default is `"automatic"`". A new `Response(body, init)` built without it would make the runtime compress the stored copy a second time.

The switch is `site-worker/html-precompression.json` (`"enabled": true`). Setting it to `false` in a pull request builds a release without copies, and the Worker then serves every page uncompressed; no code change is needed. `node scripts/build-static-site.mjs --precompress-html off` does the same for a local build.

The build ID now also depends on the zlib and brotli versions in the Node.js that ran the build (recorded in `htmlPrecompression.encoder`). The offline-cache identity (`sourceGraphId`) does not.

History: compressing HTML in the Worker at request time (`CompressionStream`, PR #161) was tried on 24 Oct 2026 and removed the same day (PR #164) after the live site monitor failed and the release rolled back. Two causes are plausible. One is the Free plan's 10 ms CPU budget. The other is that #161's `src/index.js` re-created the response without `encodeBody: "manual"`, so the runtime would gzip the already-gzipped body again: the headers stay correct (the smoke test only checks headers) while every page body is unreadable. Run locally through the real `src/index.js` with that runtime rule emulated, #161 fails the same site monitor on every HTML page; the 24 Oct local check called the handler directly and never ran `src/index.js`. `site-worker/tests/worker-entry.test.mjs` now runs the real entry point under that rule.
